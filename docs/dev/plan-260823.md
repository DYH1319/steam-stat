# Steam Stat 架构与路线规划

把 Steam Stat 从「单人堆功能的桌面工具」重构成「Core 层可测试、Electron 只当外壳、Steam 接入统一收口、Local-first + 可选 E2EE 同步」的可持续开源项目，并给出明确的功能取舍与 3~6 个月执行顺序。

## 一、诊断：你的四个问题，实际上是三个问题

我读完了 `ElectronNet/`（21 个 static service、约 6000 行 C#）、`src/views/steam/` 的 7 个页面（14KB~38KB 单文件）、`AppDbContext.cs`（634 行）、CI 和 csproj。结论如下。

### 1.1 最紧急的问题，你没有列出来：**项目现在别人根本构建不了**

- <ref_snippet file="D:\DYH\Projects\MyLTSProjects\steam-stat\steam-stat\ElectronNet\ElectronNet\ElectronNet.csproj" lines="72-98" /> 硬编码了 `D:\DYH\Projects\RiderProjects\Electron.NET\` 的 `ProjectReference` 和两个 `Import`。
- CI 靠字符串替换绕过：<ref_snippet file="D:\DYH\Projects\MyLTSProjects\steam-stat\steam-stat\.github\workflows\build-and-release.yml" lines="57-68" />
- CI 只在 `tag: v*.*.*` 触发。**push / PR 没有任何构建、lint、测试**。
- `ElectronNet.Tests` 里的测试全部被注释掉、且内含 `"xxx"/"xxxxxx"` 硬编码凭据占位，等于死代码。前端 0 测试。

对一个「唯一开发者」的开源项目，这三件事叠加的后果是：**你永远得不到外部帮助，而每加一个功能，只有你一个人能手工回归测试。** 这才是「越做越臃肿、越来越迷茫」的物理原因，架构耦合只是它的表现。

### 1.2 架构问题的准确描述：不是「耦合高」，是「没有边界」

- **21 个 `static class`，无 DI，无接口**。服务之间直接按具体类型互相调用，已出现环：`SteamLibraryService → SteamAppService → GlobalStatusService`、`SteamFriendsService → SteamAppService`。
- **业务逻辑直接调 UI**：`Electron.IpcMain.Send` 出现在 4 个业务 service 深处（`SteamLoginService.cs:940`、`SteamFriendsService.cs:596`、`SteamUserService.cs:140`、`UpdateService.cs:131`）。这一条就让 Core 逻辑**在原理上无法被单元测试**。
- **`AppDbContext` 是单例 + 634 行 God Object**，6 张表的 Fluent 配置全塞在一个文件，连接串硬编码在 `OnConfiguring`。加一个功能就要改这个文件 → 天然冲突点。
- **前端 7 个页面各自重造轮子**：7 份 loading 状态、52 处结构相同的 `toast.error`、5 份「刷新按钮 + 人造 setTimeout 延迟」、5 份 lastRefreshTime。没有 Steam 领域 store，`login.vue`/`library.vue`/`user.vue` 各自重复拉同一份「已登录用户」。
- **IPC 契约在 3 个地方手抄**：`preload.mjs`（JS）、`IpcMainService.cs`（C#）、`ipc.d.ts`（TS）。改名字没有任何编译期保护，只会运行时炸。

### 1.3 「限流 / 国内网络 / SteamKit2 衔接 / 重连」是**同一个问题**

你把它们列成四个，是因为现在没有一个统一的 Steam 接入层，所以每个功能各写各的。事实：

| 问题 | 现状 | 证据 |
|---|---|---|
| 限流 | **完全没有**任何 rate limit / 请求合并 / 重试策略 | 全代码库无 Polly，无令牌桶 |
| 缓存 | 只有内存缓存（`_userLibraryCache`、`_userFriendsData`），**重启即失效** | `SteamLibraryService.cs:21`、`SteamFriendsService.cs:10` |
| HttpClient | 2 处**每次调用 new 一个**，端口耗尽风险 | `SteamUserService.cs:216`、`FileHelper.cs:29` |
| 国内网络 | 3 个 HTTP 端点里，`store.steampowered.com`、`api.steampowered.com`、`steam-chat.com` 在国内**基本都不稳定/被墙** | `SteamAppService.cs:279`、`SteamLibraryService.cs:388`、`SteamUserService.cs:214` |
| 重连 | 手写指数退避，但**不区分「暂时性失败」和「token 已失效」**，会对已死的 refreshToken 永远每 60s 重试 | `SteamLoginService.cs:685-833` |
| 回调循环 | 每个账号一个 `Task.Run` + `RunWaitCallbacks(100ms)` 忙轮询，N 账号 N 线程 | `SteamLoginService.cs:593-606` |

**关键发现（这是整份规划里最有价值的一条）：你的大部分 HTTP 调用都可以换成 SteamKit2 的 CM 协议调用。** CM 协议就是 Steam 客户端自己用的协议——**不需要 Web API Key、限流宽松得多、而且在国内是通的**（国内 Steam 客户端能登录能聊天，被墙的是 store/community 这些 HTTP 域名）。

我实际扫描了 `SteamKit2 3.4.0` 的程序集，确认以下都可用：

- `PICSGetProductInfo` ✅ → **替代** `store.steampowered.com/api/appdetails`（游戏名、类型、元数据）
- `CPlayer_GetGameAchievements_Request`（带 `language` + `hash_only` + 响应含 `schema_hash`）✅ → **这就是「成就多语言本地化」问题的完整答案**
- `GetAchievementsProgress` / `GetSharedLibraryApps` / `GetFriendsGameplayInfo` / `GetTopAchievementsForGames` / `CMsgClientGetUserStats` ✅

改造完之后，**需要走 HTTP 的只剩图片资源**（`*.steamstatic.com` CDN，国内可达性远好于 API 域名）。

## 二、北极星：先定位，再决定做什么

你的「想做的功能太多但无从下手」，根因是没有一句话能判断「这个功能该不该做」。我建议这一句：

> **Steam Stat 记录并分析 Steam 自己丢弃的数据 —— 全部在你自己的机器上。**
> *Steam Stat records and analyzes what Steam throws away — locally, on your machine.*

判据非常锋利：**Steam 自己已经展示的，你做不过它；Steam 不保存的，只有你能做。**

用四个轴给你所有想法打分（护城河 / 数据获取成本 / 每年维护税 / 是否契合本地优先）：

| 功能 | 护城河 | 数据源成本 | 维护税 | 结论 |
|---|---|---|---|---|
| **游玩时长记录与统计**（已有） | **高** — Steam 只给总时长和两周时长，无会话级历史 | 本地注册表/进程 | 极低 | **核心资产，继续加深** |
| **存档解析** | **高** — 纯本地解析，隐私天然胜过 savescope 这类网页版 | 纯本地文件 | 高，但**可外包给社区** | **最佳新赌注**（但见 §5.5，先别做插件系统） |
| **好友状态历史/时间线** | **高** — Steam 完全不保存好友在线/游戏历史 | CM（已实现） | 低 | **做，与主线完全同源** |
| **成就** | 中 — AStats/Steam 已有，但**解锁时间线 + 跨库聚合**是空白 | CM，可用 schema_hash 缓存 | 低（缓存建好后） | **做，且是最便宜的下一个功能** |
| **游戏库（自有/家庭/愿望单）** | **低** — Steam 客户端本来就做得很好 | CM | 中（家庭库边界情况多） | **降级为支撑性只读视图，不当门面功能** |
| **库存 / 饰品 / 市场价格** | 低，且触及 ToS 与灰产风险 | HTTP，国内不通，限流严 | 高 | **写进 Non-goals** |
| **「各种 Steam 小工具」** | 因项而异 | — | **千刀万剐** | **默认不做**，除非通过上面那句判据 |

### 建议立刻写进 README 的 Non-goals

对单人维护的开源项目，**公开的「不做什么」清单是最省时间的一份文档**——它同时挡住外部 issue 和你自己的 scope creep。

```
Non-goals（明确不做）
- 不做 Steam 客户端的替代品：库浏览、商店、聊天、下载管理
- 不做库存/饰品/市场价格相关功能
- 不做需要上传用户可识别数据的服务端功能（云同步为端到端加密，服务端不可读）
- 不做游戏内注入、修改存档、解锁成就等任何改动 Steam 数据的功能
```

最后一条尤其重要：**存档解析必须是只读的**。一旦沾上「改存档/解成就」，你会同时招来 ToS 风险、封号索赔和大量支持负担。

## 三、目标架构

### 3.1 解决方案结构（你选了「剥离 Core，Electron 只当外壳」）

```
SteamStat.sln
├─ src/
│  ├─ SteamStat.Core/                  ← 不引用 ElectronNET，任何情况下都不
│  │   ├─ Abstractions/                IEventBus, IClock, IAppPaths, ISecretStore,
│  │   │                               ISteamInstallLocator, IProcessWatcher, ISyncBackend
│  │   ├─ Steam/
│  │   │   ├─ Session/                 SteamSessionManager（唯一持有 SteamClient 的地方）
│  │   │   ├─ Gateway/                 ISteamGateway + 限流/重试/缓存/合并 管道
│  │   │   └─ Handlers/                RichPresence / Levels 等自定义 handler
│  │   ├─ Features/                    ← 垂直切片，功能之间不互相 using
│  │   │   ├─ LocalStatus/  Users/  Apps/  UsageTracking/
│  │   │   ├─ Friends/      Library/  Achievements/  SaveScope/
│  │   └─ Persistence/                 AppDbContext + 每个切片自己的 EntityTypeConfiguration
│  ├─ SteamStat.Platform.Windows/      注册表、进程扫描、DPAPI —— 全部实现 Core 的接口
│  ├─ SteamStat.Contracts/             IPC channel 常量 + DTO（TS 类型从这里生成）
│  ├─ SteamStat.Host.Electron/         薄壳：DI 装配 + IPC 注册 + 窗口/托盘/更新
│  └─ SteamStat.Plugins.Abstractions/  （Phase 5 才需要）
├─ tests/
│  ├─ SteamStat.Core.Tests/            纯逻辑，无 Electron，CI 里跑
│  └─ SteamStat.Architecture.Tests/    守护「Core 不得引用 ElectronNET」等铁律
├─ tools/GenerateIpcContracts/         C# → preload.mjs + ipc.d.ts 代码生成
└─ third_party/Electron.NET/           git submodule，替代硬编码 D:\ 路径
```

### 3.2 三条铁律（用架构测试强制，不靠自觉）

1. **`SteamStat.Core` 永远不引用 `ElectronNET.API`。** 用一条 `SteamStat.Architecture.Tests` 断言程序集引用列表，CI 里跑。这一条一旦立住，你所有业务逻辑立刻变得可测。
2. **Feature 切片之间不直接 `using`。** 需要跨切片时，走 `IEventBus`（领域事件）或对方发布的只读接口（如 `IAppNameResolver`）。这会直接消掉现有的两个环。
3. **业务代码不许出现 `Electron.IpcMain.Send`。** 现有 4 处全部换成 `IEventBus.Publish(SomeDomainEvent)`，由 Host 层唯一的 `IpcEventForwarder` 订阅后转发。

### 3.3 三层数据模型（对应你画的那张图）

| 层 | 内容 | 存放 | 成本/责任 |
|---|---|---|---|
| **Local First** | 游玩记录、好友状态历史、存档解析结果、登录 token | 本机 SQLite + OS 密钥库 | 零 |
| **Public Data** | 成就 schema（按 appid+language+hash）、游戏元数据、存档解析器索引 | **GitHub 仓库 + jsDelivr/CDN**，GitHub Action 定时更新 | **≈ 零成本，且国内可达** |
| **Cloud Optional** | 端到端加密的同步 blob | 用户自带（WebDAV/S3/网盘目录）**或**你托管的付费服务 | 只有托管这一项才产生成本 |

**Public Data 层是被严重低估的一步棋。** 把成就 schema、游戏名这类**非个人数据**镜像成静态 JSON 发到一个 `steam-stat-data` 仓库、走 jsDelivr/Cloudflare：

- 成本 = 0，无服务器、无数据库、无合规责任
- **国内用户直接可达**，一举解决「访问不到 Steam API」
- 所有用户共享一份缓存 → **限流问题从根上消失**（1 个 CI 任务拉，10000 个用户读 CDN）
- 天然是社区可贡献的（PR 修数据）

## 四、Steam 接入层设计（一次性解决限流/国内网络/重连/衔接）

### 4.1 `ISteamGateway`：唯一出口

```
ISteamGateway
  ├─ 数据源优先级：本地缓存(SQLite) → Public CDN → CM 协议(SteamKit2) → HTTP(最后手段)
  ├─ 限流：System.Threading.RateLimiting 令牌桶，按「主机/服务」分桶
  │        Web API 保守取 200 req / 5min；CM 按 service 单独预算
  ├─ 重试：Microsoft.Extensions.Http.Resilience (Polly v8)，指数退避 + 抖动 + 熔断
  ├─ 合并：把现有两处 ConcurrentDictionary<K, Task<V>> in-flight 去重泛化成通用组件
  └─ 缓存：SQLite 持久化，带 TTL / ETag / schema_hash，**重启后仍然有效**
```

### 4.2 HTTP → CM 迁移清单（已验证 API 可用）

| 现状 | 迁移目标 | 收益 |
|---|---|---|
| `SteamAppService.cs:279` store appdetails | `PICSGetProductInfo` | 国内可用 + 无限流 |
| `SteamUserService.cs:214` steam-chat.com/miniprofile | PersonaState + 已有 `SteamLevelsHandler` | 去掉一个必然被墙的域名 |
| `SteamLibraryService.cs:388` IWishlistService | 原始 unified message（proto 需手写）或保留 HTTP 兜底 | 可选 |
| 头像/图标下载 | 保留 HTTP，但走 `IHttpClientFactory` + CDN 域名备选列表 | 修掉 socket 耗尽 |

### 4.3 成就本地化：用 `schema_hash` 解决「太多太杂 + 多语言」

这是你专门提到的痛点，方案是现成的：

1. `CPlayer_GetGameAchievements_Request { appid, language, hash_only = true }` → 只拿 `schema_hash`，极便宜
2. 与本机 SQLite 里缓存的 hash 比对，**不一致才拉完整 schema**
3. 完整 schema 含 `localized_name` / `localized_desc` / `icon` / `hidden` / `player_percent_unlocked`，**Valve 直接给你本地化文本，你一个字都不用翻译**
4. 缓存键 = `(appid, language, schema_hash)`，同时推到 Public Data CDN，让所有用户共享

**结论：成就本地化不是 i18n 问题，是缓存问题。** 千万不要往 `src/locales/*.json` 里塞成就名——那条路会让你的 locale 文件涨到几十 MB 且永远维护不完。

### 4.4 会话管理：从 `SteamLoginService`（1008 行）里拆出来

拆成三个职责清晰的类：

- **`SteamAuthenticator`** — 只管认证流程（密码/二维码/token），一次性，用完即弃
- **`SteamSessionManager`** — 唯一持有 `SteamClient`，管理 N 个账号的生命周期
  - 用 `RunWaitCallbackAsync` 替代 `Task.Run` + 100ms 忙轮询
  - 每账号暴露状态机：`Disconnected → Connecting → LoggingOn → Ready → Reconnecting → Failed(terminal)`
  - 重连加**抖动** + **错误分类**：`ServiceUnavailable/TryAnotherCM/网络` = 暂时性可重试；`AccessDenied/InvalidPassword/Expired` = **终止重连并提示用户重新登录**（现在会无限重试死 token）
  - 订阅 `NetworkChange.NetworkAddressChanged`，断网时暂停重试而不是空转
- **`SteamTokenStore`** — 基于 `ISecretStore`（Windows=DPAPI / macOS=Keychain / Linux=libsecret）

### 4.5 降级状态机（直面「国内访问不到」）

现在网络失败 = `Console.WriteLine` + 返回空数组 → 用户看到空白页，分不清是自己网络问题、没登录、还是 bug。

引入全局网络态并在 UI 上明示：

- `Online` — CM + HTTP 均通
- `Degraded` — CM 通、HTTP 不通（**国内绝大多数用户的常态**）→ 自动切 CM/CDN 路径，静默降级
- `Offline` — 全部不通 → 展示 SQLite 缓存数据 + 「数据来自本地缓存，最后更新于 X」

外加设置项：**「国内网络优化模式」**（优先 CM/CDN、延长超时、可填自定义 HTTP 代理、SteamKit2 优先用 WebSocket CM 连接——WebSocket 比裸 TCP 穿透性更好）。

**这个 Phase 单独解决你列的问题 2 里的「限流 / 国内网络 / SteamKit2 衔接 / 重连重试」全部四项。**

### Phase 3 — 垂直切片示范：成就（3–4 周）

把「成就」作为第一个完全按新架构实现的功能，理由：纯 CM、无需 HTTP、`schema_hash` 缓存方案已明确、规模最小、且产出的 `SchemaCache` 是后面存档解析要复用的基础设施。

做完后把 Friends / Library 回填成同样的切片形态。同时前端配套：
- `src/composables/useIpc.ts`（类型安全 IPC 封装）
- `src/composables/useAsyncResource.ts`（统一 loading / error / retry / stale-while-revalidate），消灭 7 份重复
- `src/store/modules/steam.ts`（共享领域状态，消灭三个页面重复拉「已登录用户」）

### Phase 4 — 同步（Local-first + 用户自带存储 + 可选 E2EE 云）（4 周）

按你的三层设计，关键是**一个 `ISyncBackend` 接口，三种实现**：

```
ISyncBackend
  ├─ LocalFolderBackend    → 用户丢进 OneDrive/坚果云/Syncthing 目录
  ├─ WebDavBackend         → 用户自带 WebDAV
  ├─ S3Backend             → 用户自带 S3 兼容存储
  └─ SteamStatCloudBackend → 你托管的付费服务（开源核心之外的商业化点）
```

同步协议设计要点：

- **同步单元 = 每设备一条 append-only 加密事件日志**（而非整库覆盖），这样多设备合并不需要服务端参与任何业务逻辑
- **加密**：用户口令 → Argon2id → 主密钥；每条记录独立内容密钥；服务端只见到不透明 blob + 设备 ID + 序号 + 大小 + 时间戳
- 服务端因此**在原理上无法解密**，「数据绝不上传」的卖点变成更强的「上传的东西我们也看不了」

必须诚实面对的三个约束（建议直接写进文档）：

1. **Steam refresh token 永远不参与同步**，哪怕加密。token 必须设备绑定（DPAPI/Keychain/libsecret）。一旦同步 token，泄露就等于账号接管——这是一条不能破的红线。
2. **E2EE 意味着无法找回密码**。丢了口令 = 数据永久不可读。UI 上必须做恢复码 + 反复警示。
3. **你图里的 "Cloud → Analytics" 与 E2EE 直接冲突**——看不到明文就做不了云端分析。Analytics 必须二选一：要么纯本地分析，要么是与同步完全分离的、匿名的、opt-in 的聚合遥测。别混在一起。

### Phase 5 — 存档解析（4–6 周）

**明确建议：先不要做插件系统。**

理由很直接：**在有 3 个实现之前设计扩展点，必然设计出错误的抽象。** 而且 .NET 加载第三方程序集**没有任何安全沙箱**——社区插件 = 任意代码执行，对单人维护的项目是无法承受的安全责任。

分两步：

- **5a（现在做）：仓库内策展式解析器。** 解析器作为 PR 进主仓库，你 review 后随应用发布。核心工作是设计好 `SaveReport` 数据模型（sections → fields → 类型化值 / 进度 / 收集度）和一个**通用 Vue 渲染器**——解析器只产出数据，绝不产出 UI，否则你要永远维护 N 份界面。先做 2–3 个游戏（空洞骑士、以撒这类存档格式清晰的）验证模型。
  - 严格只读：只读存档文件，绝不写回。
- **5b（当 PR 量真的成为瓶颈时再做）：WASM 插件。** 到那时再抽 `SteamStat.Plugins.Abstractions`，用 `wasmtime-dotnet` 承载——WASM 是真沙箱（默认无文件/网络权限）、且语言无关（贡献者可用 Rust/C#/Go）。**不要**选 Lua/Jint，它们不是安全边界。

相比 savescope.cn（网页版、需上传存档、需注册账号、约 6 个游戏），你的差异化非常清晰：**本地解析、零上传、离线可用、和你的游玩时长/成就数据打通**。

### 跨平台（贯穿 Phase 1–3，但先不发版）

- Windows 专属部分全部收进 `SteamStat.Platform.Windows`：注册表（`Win32RegisterKeyExtention`）、`System.ServiceProcess`、DPAPI、进程名扫描
- SteamKit2 与 VDF/ACF 解析本身完全跨平台，**接口抽好之后移植大约已完成 80%**
- 但**先别发 macOS/Linux 版**：每多一个平台，你的手工 QA 负担就翻倍。等到 (a) CI 能构建并冒烟测试该平台 (b) 真的有人提需求，再发。接口抽象本身无论如何都该做，成本很低。

## 六、商业化（对应你的 Local/Public/Cloud 三层）

- **立刻可做、零成本**：开通爱发电 / GitHub Sponsors，README 挂上。这一步不需要任何架构改动。
- **开源核心（Open Core）分界线要提前画清**：`ISyncBackend` 的 LocalFolder / WebDAV / S3 三种实现**保持 MIT 开源**，只有 `SteamStatCloudBackend` 与托管服务闭源收费。这样「不想付费的用户可以完全自给自足」，社区不会反弹，而愿意省事的用户付费——这是最健康的开源商业化形态。
- **服务端只承载两类东西**：(a) 不可读的加密 blob；(b) 非个人的公共数据。永远不存明文用户数据、永远不存 Steam 凭据。这既是道德底线，也是让你晚上睡得着的合规底线（PIPL / GDPR 下，存明文个人数据你就是数据处理者）。
- **别急**：Public Data 层走 GitHub + jsDelivr 是零成本的，所以「需要收入来维持服务器」这个压力在 Phase 4 之前**根本不存在**。不要为一个还没有的成本去提前架构。

## 八、主要风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **重构中途失去动力** | 1–2 个月不出新功能，对单人项目是真实风险 | 每个 Phase 都必须可发版；Phase 0 立刻发一版（含 friends/library）拿到正反馈 |
| **上游 Electron.NET 不接你的 PR** | ElectronNET.Core 仍是 0.x | submodule 是稳妥兜底；Core 剥离之后，即使将来要换外壳（改成 Node Electron + 独立 .NET 进程）成本也已大幅降低 |
| **CM 协议未公开、Valve 可能改** | PICS/unified message 均为非官方 | 保留 HTTP 兜底路径；Public Data CDN 也是缓冲垫 |
| **.NET 10 + SteamKit2 3.4 均较新** | 升级可能引入 breaking change | 锁版本；有测试网之后升级才安全 |
| **存档解析的长尾维护** | 游戏更新会改存档格式 | 只读 + 解析失败要优雅降级；策展模式让你能控制节奏 |
| **E2EE 不可恢复** | 用户丢口令即丢数据 | 恢复码机制 + 强提示；同步默认关闭 |
